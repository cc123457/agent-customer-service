# 记忆问答新题验收：80题冻结首轮

2026-11-25，新建80条未用于本轮修复的内部客服记忆题，冻结当前业务实现、题目、评分及模型设置后一次执行。当前记忆方案严格任务通过66/80＝82.50%；仅近期历史27/80＝33.75%；同题差48.75个百分点。正文内容正确率另为71/80＝88.75%，不能把两个口径混写。

这次不再用已参与修复的24/8题充当新题效果证明。正式80题跑完后，没有据失败修改业务代码、提示词、检索参数或数据标签，也没有挑选成功重跑替换失败。之前的修复回归结果仍保留。

## 1. 先冻结，再调用

- [冻结协议](../evals/freezes/memory-qa-holdout-v1-20261125.json)：记录生产源文件、提示词、配置、评测器和评分工具SHA256，以及80题数据指纹。
- [新题](../evals/memory_qa_holdout.json)：80题、10类各8题；与旧集的问题文本、用户和编号不重叠。共55个可回答题、25个应拒答/澄清题，2598轮原始来源及干扰对话，含同会话早期信息与跨会话信息。
- 模型固定qwen3-omni-flash，Embedding固定text-embedding-v4；四方案temperature=0、max_tokens=512、enable_thinking=false、max_retries=1，评测并发1、起始请求间隔1.5秒。摘要与回答使用同一聊天模型，未使用Realtime候选，中途未切模型。
- 正式运行前只用1条旧校准题检查接口可用性，没有用新题预跑或调参；这5次预检调用不混入80题成绩。正式运行400次聊天/摘要调用均取得usage，无已记录接口失败；80题、320个计划回答均完成。
- 运行结束自动检查全部冻结指纹，验证通过。当前业务实现与上一轮修复结束时一致。本轮新增的是验收数据、冻结/复核工具和报告。

十类为：个人事实、助手处理结论、知识更正、时间与计划、多来源合并、偏好约束、指定历史时点、遗忘、无证据和不确定情形。每题近期干扰长度为22/28/34/40轮，避免全是一个固定历史长度；每题模型输入中不包含金标准或评分字段。

数据由参与过项目实现的当前助手编写，能力场景与旧集有交集，部分语言结构相似。因此它是“实现冻结后的内部新题验收”，不是外部独立盲测、随机生产样本或线上准确率。

## 2. 测的是什么

四种方案对同一题使用相同模型、回答系统策略和问题时间：

| 方案 | 输入范围 |
|---|---|
| 仅近期历史 | 当前会话最近20条消息，无摘要和跨会话召回 |
| 摘要＋近期 | 当前会话摘要和摘要水位后的近期问答 |
| 当前记忆 | 生产ChatService选择的有界摘要、长期事实、近期问答及历史片段 |
| 完整历史参考 | 本人已完成且提问时已发生的全部原始会话，使用独立32768估算单位上限 |

正式评测使用真实模型、真实Embedding、临时SQLite及独立Chroma。历史事实提取沿用既有评测器的规则分支；未运行模型事实抽取器、JWT登录、产品知识库与业务工具Agent，也未测生产Redis命中率。因此结果应称“记忆问答任务效果”，不能称整个客服Agent端到端准确率。

完整历史是参考方案，不是Oracle。它仍可能选错日期、忽略冲突、恢复已遗忘值；“把全部历史放进去”不保证答案正确。

## 3. 评分定义与逐条复核

冻结前约定的主指标为严格任务通过率：

`通过题数 / 全部80题`

每题同时要求：正文完整正确、abstain字段符合可回答/应拒答要求、不使用应遗忘或受限来源值，且结构有效。超时、格式错误、未执行和答错都不从分母移除。正文正确但abstain不一致算严格失败，同时保留正文正确这一事实。

先保留固定答案别名/禁止值的规则分数，再由当前助手逐条检查全部320个输出、截至提问时有效原文及模型实际上下文，明确写下判定、理由与逐字引用。复核记录不是从规则passed字段复制生成的。两条摘要方案回答使用“勿进”“禁拖地”等正确同义表达，AI复核判正确，原规则结果仍分别保留。

评审显示匿名输出ID，当前助手仍可能从输入结构辨别方案，且参与了数据与代码实现；不称独立盲评或真人评分。human_correct保持null，实际人工评分0条。

正文匹配与证据支持分开判断：仅近期有2题、摘要方案有1题碰巧猜对完整历史答案，但实际输入无依据。按预先定义的答案任务口径仍计入对应正确数；证据支持单列为失败。当前记忆通过的66题均有输入依据，所以没有靠排除基线的碰巧正确来放大差异。

## 5. 当前记忆的14个失败

| 类型 | 数量 | 具体原因与位置 |
|---|---:|---|
| 历史检索没有触发 | 2 | multi_session-00/02采用“把……一并告诉我”“请同时列出……”陈述式请求；memory/history_retrieval.py的history_query仅覆盖部分关键词/问句，没有触发召回 |
| 已遗忘值再次输出 | 5 | historical_time-04的日期回查恢复旧型号；forget-01/04/05/06中的“我之前的型号”“回答风格”“删除……记录”和预算笔记没有有效删除，旧事实仍参与回答 |
| 多设备未澄清却选一个 | 1 | uncertain-00中明确有客厅和卧室两台，输入也有待澄清标记，模型仍直接选客厅型号 |
| 正文正确、拒答字段错误 | 5 | no_evidence-03/06/07、uncertain-03/06均说明无订单/数据/确定型号，却abstain=false |
| 失败来源口径边界 | 1 | no_evidence-01要求“登记成功”的型号；failed轮次中的用户事实已经先提交到SQL，当前事实仍被返回，需单列产品语义争议 |

遗忘问题的代码链路：memory/long_term.py的删除正则只覆盖有限措辞，且只支持固定属性；“回复风格”和“回答风格”不是同一个匹配标签，普通笔记也没有通用删除键。services/chat_service.py在明确历史回查时保留原文，日期筛选可能只取到早期值；若没有独立的遗忘约束，旧值就会重新进入模型。memory/context_builder.py的“当前有效事实”标记不能代替正确删除，甚至会让陈旧记录更容易被采用。

这些是本轮发现的实际边界，尚未修改。不能据此继续宣称“任意遗忘表达均可靠”“历史回查不会恢复遗忘值”。后续应优先修复这类数据生命周期问题，修复后另外建立下一版验收集，保留本轮首测。

失败来源题存在明确语义边界：db/memory_repository.py的start_request先事务提交用户输入及事实，后续聊天请求失败并不会自动回滚已明确的用户事实。若产品允许这类事实继续有效，该题标签需要在下一版定义中区分“聊天失败”与“事实未提交”，不能直接归为用户隐私泄露。本轮按冻结的“登记成功”标签保守计失败，没有事后改分；若另采用允许已提交事实的解释，当前严格成绩只会增加1/80＝1.25个百分点。该题的4个评审记录均标为需人工复核，主分母仍80。

另有70次摘要成功、10次摘要未提交。后者没有被剔除，当前方案继续按原有降级路径使用近期消息、事实和历史。评测没有完整记录这10次的详细压缩失败原因，不据usage成功就断言摘要业务处理全部成功。
