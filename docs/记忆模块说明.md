## 1. 共享服务对象与每轮资料

api/deps.py 的 get_chat_service() 创建并缓存一个 ChatService。缓存的是Agent、租约、数据库、提取器和索引的组装结果，不是上一次用户的输入或回答。

~~~python
service = get_chat_service()  # 后续请求复用组件
turn_a = await service.open_turn("会话A", "我用的是X10", "用户1001")
turn_b = await service.open_turn("会话B", "清理滤网怎么办", "用户1002")
~~~

每轮输入作为方法参数重新传入，并创建新的ChatTurn。数据库查询限定认证用户和会话；多个请求不会因为共享service而共用同一份用户历史。每进程分别缓存服务，进程重启后重新组装；不要把该缓存当作跨进程全局单例或首次并发只初始化一次的严格承诺。

ChatTurn统一包含：scope、owner、messages、deadline、compression、user_id、session_id、request_id、turn_id、user_message_id、resume。

- scope：认证用户与会话编号组合出的隔离范围。
- owner：本轮随机租约令牌，不是用户ID。
- request_id：客户端可见请求编号，同用户会话重复ID返回409。
- turn_id：内部SQL轮次编号，同时定位本轮执行检查点。
- user_message_id：本轮用户原文ID，长期事实用它记录来源。
- resume：新执行为False，继续失败请求为True。

## 2. 请求入口与会话隔离

后端/login验证账号密码并签发JWT，Streamlit客户端保存token，后续放入Authorization请求头。/chat读取JSON后处理依赖，包括服务取得、JWT与按用户限流，再校验ChatRequest字段；全部通过才进入chat函数体。

open_turn先检查本轮输入预算，然后用session_scope将user_id与session_id组合。相同session_id在不同用户下仍是不同scope。客户端不能通过请求正文冒充另一个user_id。

## 3. 两层租约与持久写入

先通过SessionLeaseStore申请快速租约：Redis使用SET NX EX，内存用线程锁保护租约字典。随后申请SQL租约，SQL才是持久写入的最终处理权依据。

同会话繁忙返回409，不排队。写入和摘要提交在SQL事务中再次检查owner及有效期；旧请求不能写回或释放新请求的租约。finally释放两层租约，取消和超时也保留用户原文并标失败。

Redis不保存当前聊天的原文和摘要。控制实例保存快速租约、按用户限流和事实缓存键目录，使用独立预算与noeviction；缓存实例只存可重建的事实查询结果，使用allkeys-lfu。正式事实仍以SQL为准。REDIS_CONTROL_REQUIRED=0时允许单进程开发兜底；Docker强制设1，控制实例不可用返回503。事实缓存单独故障则旁路SQL，不能据此宣称整个系统可无条件继续接收请求。

## 4. 原文、摘要与上下文

start_request在一个短事务中保存running请求、用户原文和明确长期事实，拒绝重复request_id。snapshot读取当前摘要、水位、有限待摘要原文与近期消息；失败请求不作为普通上下文使用。

按history_window数量或估算预算触发摘要。BatchSummarizer逐批传入“指令＋阶段摘要＋本批原文”，所有选定原文成功后才提交最终摘要及summary_upto，原始消息不因摘要成功删除。摘要水位只推进到完整问答末尾。

compose_context按预算组合当前问题、近期完整问答、摘要、相关长期事实与少量历史片段。暂未选中的原文仍在SQL，但不会自动全部进入本轮上下文。预算使用UTF-8字节和固定开销估算，不是精确Token计数，也未完整覆盖图内系统提示、工具Schema及新增工具结果。

历史和近期旧轮次出现明确的未来生效日期时，pending_plan_label复用日期规则，将其标为“尚未生效”，原话及来源继续保留。ChatService传入同一个repository.clock()作为as_of，防止存储层按一种时间判断、模型却误把较晚说出的未来计划当当前值。标签开销仍计入预算；本轮用户消息不改写，模糊或作用域不明的日期不强行判断。

当前明确边界：选定原文若8批未完成或整次摘要超时，本次不提交阶段进度，下一次可能重新处理同一前缀；尚未实现可恢复摘要任务或成功前缀逐段推进。不要把本次结构清理理解成已修复这个独立问题。

## 5. 长期事实、冲突与语义召回

规则优先提取明确型号、地面、养宠、回复风格与显式笔记；规则未覆盖时可用模型补充。模型使用JSON Mode、Schema提示和Pydantic，应用继续校验值、对象、证据及有效时间来自原文，属性符合字段含义；错误最多纠正一次，接口失败保留原文并继续聊天。

services/json_payload.py仅清除模型JSON外围的代码围栏，随后继续相同严格校验，不补字段或扫描任意说明段落。明确预算使用有限稳定属性键，避免改金额后新旧预算同时作为当前值；其他自由note仍没有通用语义合并。

明确“从/自YYYY-MM-DD起/开始/生效”的更正通过memory_scheduled_facts保存计划；未到日期时保留旧事实，到期首次读取在事务中激活，并更新SQL版本使Redis旧缓存失效。日期按UTC+8零点解释。取消/删除或更新来源可以阻止旧计划复活；相对时间、复杂多日期语义及未来计划管理接口尚未覆盖。原文与事件仍保留，软删除不等于物理抹除。

profile事实兼容普通字段，有限房间对象独立存储。明确更正更新对应对象；矛盾陈述进入待澄清状态，多台设备未指明对象也提示澄清。模型可理解范围仍有限，不能声称任意自然语言冲突都能解决；有限预算键也不等于任意note之间的语义合并。

个人记忆独立Chroma集合与产品RAG分离。先按用户过滤语义候选，再回SQL检查active状态和内容/来源指纹；进入模型的是SQL正文。删改后即使向量暂未同步，也不能仅凭旧索引返回失效内容。索引故障记录警告并退回词法查询。

### 5.1 结构化事实Redis缓存

原来每轮search_memories都查询SQL中的设备型号、地面、养宠和回复风格；现在这四类字段查询先读取SQL用户记忆版本及最近待生效时间，再查询Redis。普通命中仍是一条版本SELECT；发现计划到期才进入激活事务。命中省去这一次结构化事实正文查询；未命中执行原SQL并回填，普通笔记、冲突查询、向量同步与SQL复核继续走原路径。它不是回答缓存，不会跳过Agent或全部数据库操作，也不是高并发容量已经验证的证明。

新增memory_cache_versions表，不ALTER已有表。start_request中事实新增、更正、显式遗忘和冲突状态变化，与版本递增在同一SQL事务完成；delete_memory成功时也在事务内递增。失败回滚不会留下一个单独成功的版本更新。读取者使用SQL最新版本构造键，因此另一个进程即使没连接Redis，正式写入也会让旧缓存逻辑失效。

应用写入采用“事务推进版本＋读取时按需回填”，不是数据库改完自动把新正文推送Redis。通过聊天更正/遗忘或删除API写入时会推进版本，下一次需要该字段时读取新版本缓存；不存在则从SQL加载并回填。直接在数据库工具里手工UPDATE事实正文不会自动推进版本，应通过仓库方法修改，或在同一事务中更新对应用户版本；否则旧缓存可能一直使用到TTL到期。

缓存键包含数据库、用户、字段组合、结果上限的哈希和SQL版本。SQL提交后，start_request、delete_memory和未来计划激活使用已提交版本通知缓存；控制Redis目录返回旧键，由缓存实例定向删除，成功后以目录原值CAS确认移除。目录异常时SQL版本仍使旧键不可供新版本请求使用，后续访问继续回收。旧发布者登记15秒写入租约，发布后再次确认版本；并发更正已发生时删除其旧键。每个数据库/用户最多登记32个正文键，满额先回收最早登记/续期的非发布项，不能把它称为逐次命中更新的严格LRU。

并发请求在更新提交前已经取得旧版本时，仍可能完成旧快照读取。跨两个Redis实例不存在统一原子事务；崩溃的发布者及连接失败可能使物理删除延迟，SQL版本检查与TTL继续兜底。人工还原数据库、重置版本表或丢失控制目录时，需协调重建/切换缓存命名空间，不能承诺无目录仍能完整枚举所有副本。

非空结果默认7200秒加0～600秒抖动；有效命中且剩余TTL不超过3600秒时才续期。空结果300秒且不续期，单条最多65536字节。读取使用Lua同时取得正文与PTTL；续期Lua比较原正文并限制业务失效时间，不会覆盖已改变的键。明确expires_at的缓存边界已有校验，但普通记忆的失效时间提取、SQL有效期和统一后台清理属于后续阶段，尚未完成。

JSON、用户、版本、来源等校验失败重新读SQL；Redis故障冷却5秒，SQL异常直接传播。连接池设置2秒连接/命令超时并关闭SDK额外自动重试；这不是整条请求严格2秒截止时间。独立缓存启动不可用时可在冷却后重新验证恢复；未配置FACT_CACHE_REDIS_URL或策略不合要求时不借用控制实例缓存正文。

同进程用固定64把条带锁合并同键冷读回填，避免按用户创建无限增长的锁；跨进程冷读仍可能重复查SQL，尚未实现分布式回填锁。缓存不是本地Chroma部署或共享索引锁问题的修复。

GET /memories/cache-stats需要JWT，只返回本人当前后端进程计数。原有hits、misses、bypasses、sql_loads、errors、invalid_entries、oversized、invalidations保留，新增refreshes（实际续期）、reclaimed_keys（删除后确认回收目录项）、publication_bypasses（发布被拒绝）和stale_bypasses（旧版本回源）。hits是有效缓存命中，misses是可访问但缺失/无效；旁路另计。sql_loads不含版本检查、遗忘规则或其他SQL。hit_rate=hits/(hits+misses)，无样本返回null。

统计保存在进程内，最多保留最近1024个用户，重启或统计淘汰后归零；多worker不聚合，不能将某一个worker的结果当作整个集群命中率。默认缓存开启，可在config/memory.yml的fact_cache.enabled关闭。实现入口为db/memory_factory.py，缓存读取和事务版本更新统一在db/memory_repository.py。

### 5.2 历史会话混合检索：按请求进入顺序阅读

**为什么改**：原来services/chat_service.py只在问题含“上次/以前/之前/历史/那次”时调用SQL子串匹配；db/memory_repository.py的旧search_history只搜索用户原话，按新旧返回5条。解决办法若只在助手回答中，或问题换了说法，就容易漏掉，而且只拿用户原话无法恢复当时的解决过程。旧search_history已删除，没有保留第二套运行路径。

**第一步：确定是否回查、回查哪个范围。** services/chat_service.py调用memory/history_retrieval.py的history_query。现在问句、“最后怎么处理的”、方案等表达也可以触发，不再仅依赖原来的五个词；普通问候和没有检索意图的事实陈述跳过。这仍是确定性规则，不是通用意图模型。支持UTC+8的今天、昨天、前天、最近N天和YYYY-MM-DD单日/双日期区间；“当前会话”限制为当前session_id。复杂时间表达尚未自动解析，可以用搜索API显式指定时间。

**第二步：先过滤，再生成候选。** db/memory_repository.py的history_turns负责SQL：强制认证user_id、可选session_id和轮次起始时间范围；只取completed状态且具有user/assistant双方消息的问答，排除已在近期窗口中的轮次。先执行过滤，再按用户消息ID取最近max_turns轮，默认200轮；不是全量历史的无限搜索。时间before是排他上界，明确日期区间则包含最后一天。

**第三步：恢复原文。** HistoryRetriever批量调用MemoryArchive.hydrate，热原文与尚在保留期内的gzip冷原文都参与检索。已过期或不完整的问答不使用；冷文件缺失/校验损坏抛HistoryArchiveError，API明确503，不伪称没有记录。SQL仍保存来源ID、会话与轮次，索引不是原文存档。

**第四步：两路召回。** _lexical在过滤后的双方原文上使用jieba分词和BM25Plus，排除零词重叠文档；关键词只出现在助手回答里也可命中。HistorySemanticIndex使用独立data/history_index和conversation_history_v1集合，整轮文字按1000字符、150字符重叠分块；只为新增/变化的块分批生成Embedding。查询前以数据库分区、用户和本次允许的轮次ID过滤；索引持久化向量及元数据，不再另存原文正文。它与产品知识库、长期事实集合相互独立。

只有日期/会话范围而没有主题词时，直接按范围的新旧读取，不执行泛化语义搜索。例如“昨天聊了什么”从已过滤范围取最近若干问答；返回仍受result_limit限制，不能理解为昨天全部聊天的完整汇总。

**第五步：融合并再次核对。** 同一轮的多个向量块只保留最高相似度，每条通道再按turn_id去重；RRF累加1/(60+rank)，默认每路最多12个候选，最终最多3轮。融合后回SQL重新核对用户、状态和时间范围，恢复当前原文并比较整轮指纹；索引中的伪造/失效候选不能直接进入模型。没有额外Cross-Encoder或LLM重排。Embedding/Chroma异常记录警告并退BM25；SQL异常继续向上传播。

**第六步：进入上下文。** memory/context_builder.py的format_history_turn给问答加会话、轮次、消息ID和UTC+8时间标记，把双方放在同一个参考块中。历史预算从800提升到1600估算单位，总预算8192不变；放不下时均衡截取双方并标“原文节选”，不能只留下问题而截掉全部回答。明确回忆旧事时保留当时原话，并标“不代表当前事实”；普通问题继续遮蔽已更正/遗忘的已知旧值。SQL原文不会因上下文截取而改变。

**依赖和接口在哪。** api/deps.py的get_history_retriever组装SQL、冷档案和可选历史向量索引；聊天服务与GET /history/search复用该组件，搜索接口不初始化Agent。接口需要JWT和按用户限流，参数为query、可选session_id、after、before；显式参数优先于问题内的日期，不带时区的时间按UTC+8解释。返回turns，每项包含来源、messages双方原文、RRF score与matched_by。main.py关闭已经创建的历史客户端。历史索引目录已加入.gitignore。

**本版边界**：默认只在过滤后的最近200轮内检索，可调整max_turns或用会话/时间缩小范围；首查可能补建缺失向量，尚未加入后台索引任务。向量同步使用有限条带锁，没有全局锁包住所有用户Embedding，但仍不是高并发容量验证。本地PersistentClient不应被多个进程并发写同一目录。过期原文由SQL/冷档案状态阻止返回，旧向量的物理定期清理尚未接入；索引可独立重建，不能当作唯一存档。本轮程序测试的可控向量只能验证流程，不能证明真实语义召回质量。

## 6. Checkpointer与恢复

每轮turn_id对应独立图线程，避免每轮组装好的历史再次追加到一个无限累积的线程。图状态与pending writes保存到同一关系库的独立表中。

- GET /conversations/{session_id}/requests/{request_id}/checkpoints：本人请求的有限状态概况。
- POST /conversations/{session_id}/requests/{request_id}/resume：继续本会话最后一条失败请求，返回SSE。

恢复重新验证身份和租约，不再追加用户输入、不重新提取图外事实；已成功查询的节点可以复用。只支持最新失败请求，不允许把旧失败回答插回已有后续对话。原文管理与长期事实在图外，恢复检查点不会自动回滚它们，也不会回滚代码或外部业务操作。

## 7. 配置与存档管理

config/memory.yml的service集中放聊天策略：history_window=20、context_budget=8192、summary_budget=1024、summary_input_budget=16000、summary_timeout=20秒、retry_cooldown=30秒、turn_timeout=90秒、lease_seconds=120秒、max_summary_batches=8、compression_timeout=40秒、long_term_budget=1200、archive_budget=1600。

extraction控制模型补充；fact_cache控制结构化事实Redis缓存；semantic控制个人记忆索引；history_retrieval控制历史候选窗口、BM25/RRF和独立语义索引；retention控制热正文/笔记/回答配额、冷热保留、摘要版本和整线程检查点清理。已经删除无效的Redis消息容量、消息TTL等配置。

~~~powershell
python scripts/init_memory_db.py --env-file .env
python scripts/maintain_memory.py --env-file .env
# 上一条默认预览；确认应用保留策略时才加--apply
python scripts/maintain_memory.py --env-file .env --apply --limit 100
~~~

原文转冷存储先导出gzip JSONL并校验SHA256、条数和内容，再事务保存索引并清空热正文，保留消息ID和来源外键。历史接口按索引读取冷正文；文件损坏或缺失明确报错。默认目录为本机磁盘，需独立备份；维护命令没有自动安装为定时任务。

不配置MEMORY_DATABASE_URL时使用独立data/memory.db，配置后可用MySQL；连接失败不静默切库。原演示业务agent.db独立保留，修改URL不会自动迁移旧档案。Docker MySQL叠加配置见docker-compose.mysql.yml。
