# 面试复盘：企业级智能客服 Agent

> 本文档用于面试前集中复习，覆盖项目全貌、核心技术点、bug 修复案例和口述稿。

## 一、项目一句话主线

**把一个「能跑通、但只能自己点着玩的 demo」，改造成「企业级 Agent 后端服务」。**

技术栈：LangChain 1.0 + LangGraph（ReAct Agent）· FastAPI（异步 SSE）· Streamlit 前端 · Chroma 向量库 · SQLite + Redis · JWT · Langfuse · MCP。

## 二、五个词框架（改造总览）

面试官问「你做了哪些改造」，先抛这五个词，再逐个展开：

| 关键词 | 任务 | 改了什么 | 为什么 |
|---|---|---|---|
| **服务化** | A+E | Streamlit 单体 → FastAPI 后端 + SSE 流式 + 前后端分离 | demo 只能人点，企业级要能被调用 |
| **分层** | C | 一坨代码 → api / services / agent 三层 | 单一职责，好维护、好测试、好扩展 |
| **有状态** | B | 无记忆 → 按 session 多轮记忆（Redis） | 客服要记得上下文 |
| **真实数据** | D | random/写死/读 CSV → SQLite | 假数据是 demo 最容易露馅的地方 |
| **可观测/安全** | 阶段2 | JWT + 限流 + Langfuse + MCP | 安全、稳定、可监控 |

## 三、架构演进

## 四、核心技术点（是什么 → 为什么 → 怎么答）

### 1. 分层架构

- **结构**：`api`（路由）→ `services`（业务）→ `agent`（核心），依赖只能向下。
- **为什么**：单一职责、可测试（业务层不 import FastAPI）、可扩展（加新入口只动 api 层）。
- **核心原则**：业务层不 import HTTP 框架；依赖单向，上层不 import 下层以外的东西。

### 2. Tool / MCP / Skill 的区别

三者**不同层次**，别放一起比：

- **Tool** = 一个「能被模型调用的函数」（能力最小单元）；
- **MCP** = 「接入外部工具的**标准协议**」（接入通道，不是工具本身）；
- **Skill** = 一份「完成任务的**操作手册**」（能力组合 + 流程知识）。

**选型**：项目内部逻辑（查库、RAG）用 `@tool`；第三方外部服务（天气）用 MCP；一套多步骤流程用 Skill。

**关键点**：MCP 接入的工具，最终在 Agent 里也是 tool，只是「来源」是外部 server。

### 3. JWT 认证

- **原理**：JWT = 盖了数字签名的通行证，三段（header/payload/signature），**能看不能改**（编码非加密）。
- **核心特性**：**无状态**——服务器不存 token，验签认人，天然适合分布式。
- **落地**：`/login` 签发（sub=user_id + exp 过期时间）→ `get_current_user` 鉴权依赖 → user_id 经 **runtime context** 注入 Agent 工具。
- **为什么 user_id 走 context 而非工具参数**：user_id 是「系统确定的事实」（来自鉴权），不该让模型决定/转述——模型传参不可靠（传错、被提示词注入越权），context 是程序直读、绝对可信。通用原则：**系统已知、可信、不该由模型自由发挥的信息，走 context 注入**。

### 4. 限流（固定窗口 → 滑动窗口 → Lua）

- **针对什么**：`/chat` 接口的调用频率，按 `user_id` 限流（不是会话记忆）。
- **演进**：内存固定窗口（deque）→ Redis ZSET 滑动窗口（时间戳当 score）→ **Lua 脚本原子化**。
- **为什么 Lua**：pipeline 只能保证「命令」原子，没法覆盖「计数→判断→记录」的 check-then-act 竞态；Lua 脚本在 Redis 服务端**整体原子执行**（Redis 单线程执行 Lua 时不处理其他命令），彻底消除并发超发。
- **接口不变 + 降级**：`is_allowed` 接口不变，Redis 挂了自动降级内存。

### 5. Langfuse 可观测性

- **是什么**：LLM 应用的可观测性平台，记录每次调用的完整执行树（模型/工具/检索的耗时、token、成本）。
- **接入**：LangChain 的 CallbackHandler，**不侵入业务代码**，`config={"callbacks": [...]}` 传入即可。
- **价值**：黑盒拆成可定位的树，哪步慢/贵一目了然；metadata 注入 user_id 可按用户筛选。

### 6. 同步 / 异步

- **本质**：同步 = 傻等（打电话）；异步 = 挂起去干别的（发微信）。
- **语法**：`async def` 定义、`await` 等待、`async for` 迭代。
- **「由同步得异步」三件套**：`def` 加 `async`、调用加 `await`、迭代改 `async for`。
- **传染性**：同步/异步要求沿调用链传导——工具异步 → 链路必须异步 → 中间件必须异步。

## 五、Bug 修复案例库（面试最有含金量的部分）

### 1. 向量库相对路径 bug（阶段 0）

- **现象**：项目里出现 3 个 chroma_db，一个真库两个空壳，从不同目录启动会连到空库。
- **根因**：`persist_directory: chroma_db` 是相对路径，且未像 data_path 那样套 `get_abs_path()`，跟随「启动目录」解析。
- **修复**：套 `get_abs_path()`，数据迁移、删空壳。
- **价值**：静默失败（不报错但查不到），体现排查能力和路径一致性的工程意识。

### 2. 回答开头重复用户问题（阶段 1）

- **现象**：每次回答开头都重复用户的问题。
- **根因**：`stream_mode="values"` 会在循环**第一步**把「输入 state」也推出来，此时 `messages[-1]` 正是用户问题，旧过滤条件 `if content` 太宽松。
- **修复**：加严过滤——只放行 `type=="ai"` 且无 `tool_calls` 的消息（最终回答）。

### 3. MCP 接入三连排错（阶段 2，最精彩）

接入「只有异步实现的 MCP 天气工具」，引爆三个连环 bug：

1. **同步链路调异步工具** → `NotImplementedError`（工具只实现 `_arun`）→ 链路异步化（`astream`）；
2. **异步链路调同步中间件** → `awrap_tool_call` 未实现 → `monitor_tool` 改 `async def` + `await handler`；
3. **MCP 工具 content 是 list** → `.strip()` 崩 → `isinstance` 判断兼容。

**核心洞察**：同步/异步要求沿调用链传导；排错用「起临时实例抓完整 ASGI 堆栈」定位（客户端只见「连接中断」，真异常在服务端日志）。
